# 有需要才展开的评审方法

## 任务与状态
用最少材料回答：用户要达成什么？现在从哪里开始？哪些能力保留？哪些操作独立？什么条件真的阻止下一步？失败后数据和用户停在哪里？

复杂时可画关系或状态表，但无需固定文档格式。区分事实、推断、未知；截图只能证明可见状态，不能证明隐藏入口、键盘操作、权限或后端行为。优先只读核对当前基准；不凭新稿断言旧功能已消失。

示例：下载空白模板与上传已填文件通常是两个可独立操作；解析成功可以是预览的前置条件。是否必须先下载取决于实际格式协议，不能凭按钮位置认定。覆盖旧数据则需了解匹配规则、预览和恢复能力，再判断确认方式，不能凭空添加产品功能。

## 检查深度随风险调整
入口变化关注可发现性、旧入口承接；任务关系变化关注能否从各合法起点完成任务；状态变化关注空、忙、错、取消和恢复中实际受影响的部分。权限或隐私变化核对可见/可操作边界和敏感内容；数据变更核对影响对象、失败结果、重试或撤回条件。只检查与变更相关的项目。

布局与视觉应表达真实关系：重要性由任务频率、当前意图、影响及项目惯例共同决定，不能机械规定每屏只有一个操作。辅助功能可以弱化，但需要可发现；渐进披露不等于隐藏必需入口。

## 有依据的分歧
例如审查者 A 主张突出“导入”，B 主张突出“导出”。先查当前页面任务和使用证据；若页面主要供生成对外报表，突出导出有依据。若缺少频率证据，不能假称用户更常导出；可依据明确的当前任务给可逆建议，说明假设。若取舍会显著阻碍另一群体且证据不足，给用户简短的影响比较和待决事项。

每条关键异议可记录为“场景 → 证据/假设 → 影响 → 替代方案 → 决定/待决”。不要求所有意见都采纳。复核只围绕尚未解决的问题或修改造成的回归。
